# Sales Data Mart

## О проекте

Учебный проект по построению ETL-пайплайна и аналитической витрины продаж с использованием Apache Airflow и PostgreSQL.

Пайплайн получает ежедневный инкремент данных через API, загружает его в Yandex Cloud Object Storage, обрабатывает данные и загружает их в Staging PostgreSQL. После этого обновляются справочники, таблица продаж и витрина удержания и возвратности клиентов.

Основной поток данных:

**API → S3 → Apache Airflow → PostgreSQL Staging → Data Mart**

## Что реализовано

* автоматизировано получение отчёта через API;
* реализовано ожидание готовности отчёта с использованием `task_id`;
* получен идентификатор ежедневного инкремента данных;
* реализована загрузка CSV-файла из Yandex Cloud Object Storage;
* выполнена предварительная обработка данных с помощью pandas;
* удалены технический столбец `id` и дубликаты по `uniq_id`;
* добавлена обработка статуса заказа и возвратов;
* реализована загрузка данных в PostgreSQL Staging;
* настроено обновление справочников клиентов, товаров и городов;
* реализовано обновление фактов продаж;
* создана аналитическая витрина удержания и возвратности клиентов с недельной агрегацией;
* весь процесс автоматизирован в Apache Airflow.

## ETL-процесс

### 1. Получение данных

Airflow запускает последовательность задач:

generate_report
      ↓
get_report
      ↓
get_increment

Сначала через API формируется отчёт, затем DAG проверяет его готовность и получает `report_id`. После этого запрашивается идентификатор доступного инкремента.

Для передачи идентификаторов между задачами Airflow используется **XCom**.

### 2. Загрузка в Staging

После получения `increment_id` DAG загружает файл `user_order_log_inc.csv` из Yandex Cloud Object Storage.

Перед загрузкой выполняется обработка данных:

* удаляется столбец `id`;
* удаляются дубликаты по `uniq_id`;
* при отсутствии `status` устанавливается значение `shipped`;
* для заказов со статусом `refunded` сумма `payment_amount` преобразуется в отрицательную.

Обработанные данные загружаются в таблицу `staging.user_order_log`.

### 3. Обновление Data Mart

После загрузки Staging последовательно обновляются:

* `mart.d_item` — справочник товаров;
* `mart.d_city` — справочник городов;
* `mart.d_customer` — справочник клиентов;
* `mart.f_sales` — факты продаж;
* `mart.f_customer_retention` — аналитическая витрина удержания и возвратности клиентов.

Для справочников используется логика добавления новых записей, отсутствующих в целевых таблицах.

## Customer Retention

Витрина `mart.f_customer_retention` рассчитывает показатели в недельном разрезе по товарам.

В зависимости от количества заказов за период клиенты классифицируются как:

* **new customers** — один заказ за период;
* **returning customers** — более одного заказа;
* **refunded customers** — клиенты, у которых были возвраты.

Для каждой категории рассчитываются количество клиентов и выручка.

Витрина также содержит количество возвратов и идентификатор недели.

## Результат

В результате реализован автоматизированный ETL-процесс от получения ежедневного инкремента через API до формирования аналитической витрины в PostgreSQL.

Проект демонстрирует навыки:

* разработки DAG в Apache Airflow;
* работы с API и асинхронным получением отчётов;
* загрузки данных из S3;
* обработки CSV с помощью pandas;
* работы со Staging-слоем;
* построения dimension и fact таблиц;
* инкрементальной загрузки;
* SQL-трансформаций;
* формирования аналитических витрин;
* передачи данных между задачами Airflow через XCom.
